# 对话基础（M1）

> 版本前提：Spring AI 2.0.2 + Spring Boot 4.1.2。类名和行为都以这两个版本为准。

## ① 这个模块治的是哪类病

大模型本身是**无状态**的：它不保存任何会话。所谓「对话」，本质上是客户端每次把一组消息（system / user / assistant / tool）重新发给模型，模型据此生成下一条消息。

因此「对话基础」解决的是：

- **如何把一次 HTTP 请求变成合法的 Chat Completions 请求**：消息角色、顺序、模型参数、鉴权。
- **如何把模型响应变回应用可消费的数据**：提取文本、暴露错误。
- **如何管理 provider 差异**：base URL、模型 ID、密钥、超时。

它处在链路的**入口位置**：上游是 HTTP；下游是模型服务。它**不负责**：

- 记住历史（那是「记忆」模块）；
- 逐字返回（那是「流式」模块）；
- 决定调用哪个工具（那是「工具调用」模块）；
- 计费与审计（那是「可观测性」模块）。

典型失败模式：

1. **鉴权失败**：key 缺失、错误、或与 provider 不匹配。
2. **地址 / 模型不匹配**：base URL 拼错、model ID 是该 provider 不认识的字符串。
3. **消息结构非法**：角色顺序错误、必填字段缺失、请求体编码不是 UTF-8。
4. **上下文超限**：单次消息过长或历史过多，请求直接被拒（不是自动截断）。
5. **同步阻塞 / 超时**：调用方没有超时预算，线程被长期占用。

## ② Spring AI 官方怎么做

**入口**：`org.springframework.ai.chat.client.ChatClient`。

- `ChatClient` 是面向应用的流畅 API；`ChatClient.Builder` 由 starter 自动装配。
- 一次同步调用的一行式写法：`chatClient.prompt().user(...).call().content()`。
- 默认系统提示词通过 `builder.defaultSystem(...)` 固定，避免每次请求重复传。
- provider 连接参数由 `spring.ai.openai.*` 配置绑定，starter 负责创建底层模型 Bean。

**能力边界（2.0.2 前提）**：

- `ChatClient` 本身**不是记忆**。不显式加 `ChatMemory` / Advisor 时，每次 `prompt()` 只包含本次传入的消息。
- 同步 `call()` 返回完整响应；流式要走 `stream()`（具体形态待 M3 验证）。
- 工具调用需要显式注册工具（具体机制待 M5 验证）。
- 官方 Reference：<https://docs.spring.io/spring-ai/reference/>

**本项目观察到的实现细节（2026-11-03 实测）**：

- Spring AI 2.0.2 的 OpenAI 集成底层使用官方 **OpenAI Java SDK**（异常栈可见 `openai-java-core-4.80.0.jar`），不是早期版本中自研的 HTTP 客户端封装。
- 缺少 API key 时，**应用仍能启动**；错误延迟到第一次调用，表现为 `com.openai.errors.UnauthorizedException: 401: Unknown`。
- 官方 docs 与示例可能仍以 1.x 为主；升级或照抄时先确认版本。

## ③ 本项目为什么这么落地

当前只做**最小闭环**，目标是先证明「配置正确、协议通、错误可见」，而不是提前引入抽象。

| 决定 | 做法 | 理由 |
|---|---|---|
| 用 starter 自动装配 | 引入 `spring-ai-starter-model-openai` | 不重复造连接层；配置项集中且可替换 provider |
| 单独定义 `ChatClient` Bean | `config/ChatClientConfig` | 系统提示词只写一处；后续加 Advisor 有固定入口 |
| 同步调用 | `call().content()` | M1 先排除流式复杂度；同步路径最容易验证 |
| 无记忆 | 不引入 `ChatMemory` | 记忆是独立模块（M2），需要先决定存储与预算 |
| 无统一响应信封 | Controller 直接返回 `record` | 保持原生 HTTP；错误映射留给 M8 |
| 参数校验只做空值 | `StringUtils.hasText` | 只拦「必然失败」的输入；其余交给模型服务 |

不做的事情：自定义 `OpenAiChatModel`、重试、超时、熔断、鉴权、持久化。

## ④ 数据结构与流程

### 请求 / 响应

```
POST /api/chat
{"message": "用户输入"}

200
{"content": "模型输出"}
```

- 请求 DTO：`chat/ChatRequest`（`record`，单字段 `message`）
- 响应 DTO：`chat/ChatResponse`（`record`，单字段 `content`）
- 空 `message`：抛 `ResponseStatusException(400)`

### 调用流程

1. HTTP 请求进入 `ChatController#chat`（上下文路径 `/api`）。
2. 校验 `message` 非空；为空直接 400，不调模型。
3. `ChatClient.prompt().user(message)` 组装消息列表。
4. 默认系统提示词（来自 `ChatClientConfig`）自动置于用户消息之前。
5. starter 用 `spring.ai.openai.*` 配置向 DeepSeek 发起 Chat Completions 请求。
6. 取响应文本，包成 `ChatResponse` 返回。

### 配置表

| 配置 | 值 / 来源 | 作用 |
|---|---|---|
| `spring.ai.openai.api-key` | 环境变量 `DEEPSEEK_API_KEY` | 鉴权 |
| `spring.ai.openai.base-url` | `https://api.deepseek.com`（可覆盖） | provider 地址 |
| `spring.ai.openai.chat.options.model` | `deepseek-chat`（可覆盖） | 模型 ID |
| `spring.ai.openai.chat.options.temperature` | `0.7` | 采样温度（是否生效待验证） |

### 验证记录

- 2026-11-03：真实调用 HTTP 200；空 `message` HTTP 400；无 key 调用 HTTP 500（根因 401）。
- 详细记录见 [05-当前实现与验证](05-当前实现与验证.md)。

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- 没有多轮记忆：第二次请求看不到第一次的内容。
- 没有流式输出：完整生成后才返回；无首 token 延迟指标。
- 没有工具调用、RAG、MCP。
- 没有超时、重试、限流、熔断。
- 没有鉴权：任何能访问 8103 的人都能消耗模型额度。
- 没有 token 统计与成本记录。
- 没有统一错误响应：400/500 是框架默认格式，原因字段被隐藏。

### 坑（现象 → 原因 → 规避）

1. **应用启动成功，但第一次对话 500**
   - 现象：无 key 也能启动；调用返回笼统 500。
   - 原因：Spring AI 2.0.2 不在启动期校验 key；错误在请求时由 OpenAI SDK 抛出（401）。
   - 规避：把 key 是否可用来作为**调用前检查**，不要只看进程是否起来；M8 补启动期校验。

2. **改了 base-url 但忘了改 model / key**
   - 现象：换 provider 后 401 或 model not found。
   - 原因：三者绑定的是同一家服务；不同 provider 的 model ID 是不同字符串。
   - 规避：三个配置一起改，改完立刻真实调用一次。

3. **base-url 写不写 `/v1`**
   - 现象：担心 URL 拼接错误。
   - 原因：不同框架对 base URL 的拼接方式不同。
   - 规避：本项目实测 `https://api.deepseek.com`（不写 `/v1`）可用；换版本后重新验证。

4. **空 message 的错误原因看不到**
   - 现象：只返回 `{"status":400,"error":"Bad Request"}`，没有「message 不能为空」。
   - 原因：Spring Boot 默认 `server.error.include-message=never`。
   - 规避：这是当前有意保留的原生行为；统一错误时再决定是否暴露原因（M8）。

5. **中文请求体变乱码 / 400**
   - 现象：终端直接 `-d '{"message":"中文"}'` 时偶发非法 UTF-8。
   - 原因：Windows 终端编码可能是 GBK。
   - 规避：写 UTF-8 文件，用 `curl --data-binary @文件`。

6. **上下文路径导致路径不一致**
   - 现象：Controller 写 `/chat`，实际访问是 `/api/chat`。
   - 原因：`server.servlet.context-path=/api` 会加到所有路径前。
   - 规避：文档与 curl 示例统一写完整路径 `/api/chat`。
