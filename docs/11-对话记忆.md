# 对话记忆（M2）

> 版本前提：Spring AI 2.0.2 + Spring Boot 4.1.2。快照时间：2026-11-07。
> 状态：✅ 2026-11-07 完成（MySQL 8.0.39 实测）。

## ① 这个模块治的是哪类病

大模型不保存会话状态。所谓「多轮对话」，是应用在每次请求时把历史消息重新拼进 prompt。记忆模块要解决的是：

- **会话边界**：哪些消息属于同一个会话，如何隔离不同用户 / 不同会话。
- **存储**：历史放在内存、数据库还是缓存；重启后是否还在。
- **预算**：最多带多少历史；超了先丢谁。
- **裁剪**：不能把「user 提问 / assistant 回答 / tool 调用 / tool 结果」这一组消息拆散。
- **并发**：同一会话同时发两条消息时，后写的是否覆盖先写的。

典型失败模式：

1. **串话**：会话 ID 缺失或复用，A 能看到 B 的历史。
2. **上下文溢出**：历史无限增长，最终请求被模型服务拒绝。
3. **裁剪破坏消息配对**：保留 assistant 回答却丢掉对应 user 提问。
4. **重启失忆**：记忆只放内存，进程重启后丢失。
5. **并发覆盖**：两个请求同时读旧历史、写新历史，其中一轮被覆盖。
6. **无界增长**：会话数只增不减，存储和内存都被拖垮。

## ② Spring AI 官方怎么做

**核心接口**（`org.springframework.ai.chat.memory`，2.0.2 实测存在）：

- `ChatMemory`：按 `conversationId` 增删查消息，常量 `ChatMemory.CONVERSATION_ID` 是上下文 key。
- `ChatMemoryRepository`：底层存储接口，只负责按会话读写整组消息。
  - 方法：`findConversationIds` / `findByConversationId` / `saveAll` / `deleteByConversationId`。
  - `saveAll` 的语义是**替换**该会话的全部消息，不是追加。
- `MessageWindowChatMemory`：官方实现，按**消息条数**保留窗口。
  - `maxMessages` 控制窗口大小，默认 20。
  - 超限时优先保留 `SystemMessage`，并把裁剪起点**对齐到最近的 USER 消息**，避免留下没有提问的回答。
  - 只按条数裁剪，**不做 token 估算**。
- `InMemoryChatMemoryRepository`：官方内存实现，进程重启即丢失。

**请求侧装配**：

- `MessageChatMemoryAdvisor` 在调用前把历史消息拼到 prompt 前，并把系统消息移到最前；调用后把 assistant 回答写回记忆。
- 会话 ID 通过 advisor 参数传入：

  ```java
  chatClient.prompt()
      .user(message)
      .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
      ...
  ```

**自动装配**：`spring-ai-autoconfigure-model-chat-memory` 默认用 `@ConditionalOnMissingBean` 提供内存版 `ChatMemoryRepository` 和 `ChatMemory`。自定义 Bean 会让默认实现回退。

**能力边界（2.0.2）**：

- 没有 token 级预算；窗口只按消息条数裁剪。
- `MessageWindowChatMemory` 不负责会话过期清理。
- `saveAll` 的「替换」语义意味着底层实现每次写入整组消息；这是接口约定，不是本项目额外设计。

## ③ 本项目为什么这么落地

| 决定 | 做法 | 理由 |
|---|---|---|
| 存储用 MySQL | 自研 `JdbcChatMemoryRepository` | 本项目要求多轮记忆在重启后仍然存在；内存方案已在 M1 排除 |
| 窗口按条数 | `MessageWindowChatMemory`，默认 20 条 | 先复用官方裁剪逻辑，避免自研预算算法；token 预算留到 M8/M6 再评估 |
| 会话 ID 由前端生成 | 请求体传 `conversationId`（UUID） | 后端不维护「创建会话」状态，接口无状态；新会话 = 换一个 ID |
| 不引入 Advisor 链之外的抽象 | 在 `ChatClient` 上注册 `MessageChatMemoryAdvisor` | 记忆是横切能力，放默认 advisor 后业务代码只传会话 ID |
| 消息类型只持久化 user / assistant / system | TOOL 类型直接报错 | 工具调用在 M5 才出现；提前存不可还原的结构只会制造假兼容 |
| 建库建表脚本独立维护 | 项目根 `sql/schema.sql`，手工执行 | 建表属于部署步骤；不让应用启动时隐式改库，SQL 可见、可审查 |

**备选方案与为什么不选**：

- **纯内存（`InMemoryChatMemoryRepository`）**：最简单，但重启丢失，不满足本项目 M2 的落库要求。
- **Redis**：适合多实例和 TTL，但引入额外中间件；当前是单机学习项目。
- **自研 token 预算裁剪**：需要 tokenizer 和模型上下文窗口参数，误差口径未验证；先不做。

## ④ 数据结构与流程

### 请求 / 响应

```
POST /api/chat
{"message": "我叫 Alice", "conversationId": "3f2c...-uuid"}

200
{"content": "你好，Alice"}
```

- 请求 DTO：`chat/ChatRequest`（`record(String message, String conversationId)`）
- 响应 DTO：`chat/ChatResponse`（`record(String content)`，未改）
- 校验：`message` 非空；`conversationId` 非空且长度 ≤ 64。不校验 UUID 格式。
- 错误：校验失败 → HTTP 400；模型或数据库异常 → HTTP 500。错误原因默认不出现在响应体（`server.error.include-message=never`）。

### 调用流程

1. 请求进入 `chat/ChatController#chat`，校验两个字段。
2. `ChatClient.prompt().user(message)` 组装本次用户消息。
3. `.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))` 指定会话。
4. `MessageChatMemoryAdvisor#before` 从 `JdbcChatMemoryRepository` 读取该会话历史，拼到用户消息前。
5. `MessageChatMemoryAdvisor#before` 把本次用户消息写回记忆。
6. 调用 DeepSeek，得到回答。
7. `MessageChatMemoryAdvisor#after` 把 assistant 回答写回记忆。
8. 返回 `{"content": "..."}`。

### 表结构

建库建表脚本：`sql/schema.sql`（项目根目录，手工执行；应用不会自动建表）。

```sql
CREATE TABLE IF NOT EXISTS chat_message (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    conversation_id VARCHAR(64)  NOT NULL,
    message_type    VARCHAR(16)  NOT NULL,  -- USER / ASSISTANT / SYSTEM
    content         MEDIUMTEXT   NOT NULL,
    created_at      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_chat_message_conversation (conversation_id, id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci;
```

- 查询按 `id` 升序还原消息顺序。
- `JdbcChatMemoryRepository#saveAll` 先 `DELETE` 再批量 `INSERT`，整体在一个事务里；这直接对应接口的「替换」语义。
- 写库频率：每轮对话写两次（用户消息一次、回答一次），每次都重写该会话当前窗口内的全部消息。

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- **无鉴权 / 无归属校验**：知道 `conversationId` 的人就能读写该会话历史。UUID 只降低了猜测概率，不是安全边界。
- **无会话 TTL / 清理**：单会话最多 20 条，但会话数量无上限，`chat_message` 会持续增长。
- **无 token 预算**：20 条长消息仍可能超出模型上下文（具体上限未实测）。
- **无并发控制**：同一会话并发写时，后提交的 `saveAll` 会覆盖先提交的窗口内容。
- **不支持工具消息持久化**：遇到 `TOOL` 类型会抛异常；M5 需要扩展表结构或改用可序列化格式。
- **未保存消息 metadata / 多媒体**：只保留文本和角色。
- **无历史查询接口**：前端刷新后只能靠自己保存的 `conversationId` 继续对话，无法从后端拉取历史消息列表。
- **无多实例一致性**：单机 MySQL 可用；多实例共享同一库时，`saveAll` 的覆盖语义会更频繁地互相踩踏。
- **模型调用失败时用户消息已落库**：`MessageChatMemoryAdvisor` 在调用模型前写入 user 消息，调用失败不会回滚；下一次提问会带上这条失败的消息。

### 坑（现象 → 原因 → 规避）

1. **旧前端不传 `conversationId` 直接 400**
   - 现象：M1 的 `{"message":"..."}` 请求全部失败。
   - 原因：M2 把 `conversationId` 定为必填。
   - 规避：前端按 [前端对接文档](frontend/README.md)（1→4）改造；联调阶段两个字段一起传。

2. **数据库或表不存在，应用启动直接失败**
   - 现象：M1 时无 API key 也能启动；M2 后 MySQL 不可用或库/表未初始化会启动失败。
   - 原因：Hikari 在启动期建立连接池，库不存在直接连不上；表缺失则要等到第一次对话才暴露。
   - 规避：先执行 `sql/schema.sql`，再确认 3306 可连；这属于有意的「尽早失败」，不要用懒加载掩盖配置问题。

3. **`saveAll` 的实现看起来在「重复写历史」**
   - 现象：每轮对话都 `DELETE` + 批量 `INSERT` 当前窗口。
   - 原因：`ChatMemoryRepository.saveAll` 的约定是替换整组消息，不是追加。
   - 规避：保持契约语义；如果以后要优化成增量写，需要换存储抽象或自己实现 `ChatMemory`。

4. **裁剪后仍可能看到「半轮」消息**
   - 现象：窗口边界偶尔从 assistant 消息开始。
   - 原因：官方实现会尽量对齐 USER，但窗口内消息类型不受调用方控制；若历史本身以 assistant 开头，无法对齐。
   - 规避：正常链路（user → assistant 成对写入）不会触发；排查时先看库里该会话的消息序列。

5. **自动装配与自定义 Bean 冲突**
   - 现象：担心同时存在两个 `ChatMemory` / `ChatMemoryRepository`。
   - 原因：Spring AI 自动装配使用 `@ConditionalOnMissingBean`。
   - 规避：自定义 `JdbcChatMemoryRepository` + `ChatMemory` Bean 即可让默认内存实现回退，无需排除自动装配类。
