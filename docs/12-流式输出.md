# 流式输出（M3）

> 版本前提：Spring AI 2.0.2 + Spring Boot 4.1.2。快照时间：2026-11-07。
> 状态：✅ 2026-11-07 完成（DeepSeek 实测；本地 E2E 用 H2 代替 MySQL，见 ⑤）。

## ① 这个模块治的是哪类病

同步调用要等模型生成完才返回。回答越长，用户盯着空白页的时间越久，首 token 延迟不可见，也无法中途取消。

流式输出要解决的是：

- **感知延迟**：token 一产生就发给客户端，首字尽快出现。
- **传输协议**：用什么承载「一段一段」的数据；本项目选 SSE（`text/event-stream`）。
- **事件契约**：正常片段、正常结束、失败分别怎么表达；客户端如何判断「说完了」。
- **取消与资源释放**：用户关页面后，上游模型调用是否继续、连接和线程是否回收。
- **失败路径**：流已经开始后无法再改 HTTP 状态码，错误怎么让客户端看见。

典型失败模式：

1. **没有结束信号**：客户端只能靠超时判断结束，长回答被误判为失败。
2. **半截 JSON**：按字符切 JSON 或 SSE 帧，客户端解析崩溃。
3. **断开后继续烧钱**：客户端走了，服务端还在接收并丢弃 token。
4. **裸 500**：流开始后抛异常，客户端只看到连接被掐断，没有可诊断信息。
5. **阻塞线程**：伪流式——先同步拿完整结果，再假装分片发送。

## ② Spring AI 官方怎么做

**版本：Spring AI 2.0.2。**

- `ChatClient` 的请求规格有 `stream()`，返回 `ChatClient.StreamResponseSpec`：
  - `content()` → `Flux<String>`，每个元素是一个增量文本片段（空片段被过滤）。
  - `chatResponse()` → `Flux<ChatResponse>`，保留元数据（finish reason、usage 等）。
  - `chatClientResponse()` → `Flux<ChatClientResponse>`，保留 advisor 上下文。
- 流式请求同样经过 advisor 链。`MessageChatMemoryAdvisor` 在 2.0.2 实现了 `adviseStream`：
  - 请求前把历史拼进 prompt，并把本轮 USER 消息写入记忆；
  - 用 `ChatClientMessageAggregator` 在 Flux **正常完成时**把增量聚合成一条 ASSISTANT 消息，再写回记忆；
  - 流被取消（客户端断开）时不会触发聚合回调，因此半截回答不落库。
- 传输层不在框架职责内：Spring AI 只给 `Flux`，SSE / WebSocket / NDJSON 由 Web 层决定。
- 底层 OpenAI 集成走官方 Java SDK，流式分片来自 SDK 的流式响应。

## ③ 本项目为什么这么落地

| 决定 | 做法 | 备选 | 理由 |
|---|---|---|---|
| Web 层 | Spring MVC + `SseEmitter` | WebFlux / 直接返回 `Flux` | 项目是 Servlet 栈（`spring-boot-starter-web`）。`SseEmitter` 能显式命名事件、挂完成 / 超时 / 错误回调，便于处理取消；不引入 WebFlux。 |
| 事件设计 | `delta` / `done` / `error` | 只发裸文本 | 客户端需要区分「还有」「结束」「失败」。裸文本无法表达结束和错误。 |
| 数据格式 | JSON：`{"content":"..."}` | 裸文本 | SSE 以换行分帧，文本里的 `\n` 会破坏帧格式；JSON 序列化后换行被转义，且便于以后加字段。 |
| 上游取消 | 发送失败或 SSP 回调时 `Disposable.dispose()` | 忽略断开，等模型自然结束 | 客户端都走了，继续接收没有意义，还会占用连接并产生 token 费用。 |
| 超时 | `SseEmitter` 120 秒 | 不设 / 跟容器默认 | 长回答需要比默认 30 秒更长的窗口；120 秒是当前的经验上限，未做压测。 |
| 心跳 | 不做 | 定时发注释帧 | 当前回答通常在几十秒内结束；心跳会增加实现与测试面。长任务 / 代理超时场景再补，见 ⑤。 |
| 同步接口 | 保留 `POST /chat` | 直接用流式替换 | 同步路径是 M1/M2 的验证基线，且部分调用方不需要流式；两条路径共用同一套校验和记忆。 |

> Jackson 注意：Spring Boot 4 默认自动装配的是 Jackson 3（`tools.jackson.databind.json.JsonMapper`），
> 不是 Jackson 2 的 `com.fasterxml.jackson.databind.ObjectMapper`。控制器注入后者会导致上下文启动失败。

## ④ 数据结构与流程

### 接口

`POST /api/chat/stream`，`Content-Type: text/event-stream`。

请求体与 `/chat` 相同：

```json
{"message":"用三句话介绍你自己","conversationId":"11111111-1111-1111-1111-111111111111"}
```

事件契约：

| event | data | 时机 |
|---|---|---|
| `delta` | `{"content":"片段"}` | 每收到一个非空增量 |
| `done` | `{"conversationId":"..."}` | 上游正常结束 |
| `error` | `{"message":"模型调用失败：<原因>"}` | 上游异常 |

- 校验失败（空 message / 空或超长 conversationId）在流开始前发生，返回 HTTP 400 + 框架默认 JSON 错误体，与 `/chat` 一致。
- 流一旦开始，HTTP 状态固定为 200；模型失败通过 `error` 事件表达，而不是 500。
- `done` / `error` 之后服务端关闭流；客户端断开时不会补发 `done`。

### 流程

1. 校验请求；不合法直接 400，不创建 `SseEmitter`。
2. 创建 `SseEmitter(120_000)`，注册 `onCompletion` / `onTimeout` / `onError`，三者都会取消上游订阅。
3. 通过 `ChatClient.prompt().user(...).advisors(conversationId).stream().content()` 拿到 `Flux<String>`。
4. 订阅 Flux：
   - `onNext` → 发送 `delta`；
   - `onError` → 发送 `error`，结束；
   - `onComplete` → 发送 `done`，结束。
5. 任一 `emitter.send` 抛 `IOException` / `IllegalStateException`，视为客户端已断开：取消订阅，停止消费上游。
6. 记忆由 `MessageChatMemoryAdvisor` 处理：正常结束时聚合保存 ASSISTANT 消息；断开的流不保存半截回答。

### 配置

| 项 | 值 | 说明 |
|---|---|---|
| 事件超时 | `120_000` ms | 代码常量，暂未做成配置项 |
| 上下文路径 | `/api` | 全局配置 |
| 记忆窗口 | 20 条 | 与 M2 相同，流式与同步共用 |

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- 没有心跳 / 注释帧；长回答经过会主动断空的代理时可能被误判断开。
- 没有把超时、并发上限、每用户限流做成配置。
- 没有在断开时保存已生成的部分回答（记忆只在正常完成时聚合）。
- 没有 `usage` / token 统计；流式接口只下发文本。
- 没有重试：上游失败直接发 `error`。
- 前端尚未接入 SSE；当前契约用 `curl -N` 验证。

### 坑

1. **现象**：注入 `com.fasterxml.jackson.databind.ObjectMapper` 后，`mvn test` 的上下文测试启动失败，报 `No qualifying bean`。
   - 原因：Spring Boot 4 默认 JSON 实现是 Jackson 3（`tools.jackson.*`），自动装配的是 `JsonMapper`，Jackson 2 只在 Spring AI / OpenAI SDK 内部以传递依赖存在。
   - 规避：注入 `tools.jackson.databind.ObjectMapper`；序列化异常也从 `IOException` 变为运行时的 `tools.jackson.core.JacksonException`。

2. **现象**：客户端中途断开后日志出现 `AsyncRequestNotUsableException: ServletResponse failed to flushBuffer`。
   - 原因：`emitter.send` 写已关闭的连接，Tomcat 抛 I/O 异常。
   - 规避：发送失败即取消上游订阅；日志按 DEBUG 记录，不影响请求线程，也不会重复刷 ERROR。

3. **现象**：SSE 文本里的换行会破坏事件帧。
   - 原因：SSE 用空行分隔事件，裸文本中的换行会被客户端当成帧边界。
   - 规避：所有 data 一律 JSON 序列化后再发送，换行被转义为 `\n`。
