# 项目定位与边界

## 一句话

Polaris 是一个基于 **Spring AI 2.x** 的个人实验项目，用来走通「对话 → 记忆 → 流式 → 结构化输出 → 工具调用 → RAG → MCP」这条 Spring AI 全链路，并与已有的 LangChain4j 项目 **star-knowledge-assistant** 形成对照。

## 为什么再开一个项目

已有的 star-knowledge-assistant 已经把 LangChain4j 的深水区走了一遍：自研 Agent 状态机、中断续跑、RAG 调优、离线评测。它的问题不是「还缺一个 CRUD」，而是：

1. **框架视角单一**。LangChain4j 是「厂商适配层」，Agent 循环、状态机都由我们自己控制。Spring AI 的抽象方式完全不同（Advisor 链、ChatClient、自动装配、MCP），值得单独走一遍。
2. **需要可对照的工程结论**。同一个「多轮记忆」「流式输出」「工具调用」，两个框架各自把复杂度放在哪、坑在哪，只有各实现一次才能说清楚。
3. **新项目成本最低**。Polaris 没有历史包袱，可以直接用当前最新稳定版本，不必迁就 star 项目的依赖。

## 做什么

| 方向 | 具体目标 |
|---|---|
| 对话主链路 | ChatClient、多轮记忆、流式输出、结构化输出、工具调用 |
| 检索增强 | ETL、Embedding、VectorStore、检索 advisor、最小评测集 |
| 生态扩展 | Spring AI MCP 的客户端 / 服务端两种角色 |
| 工程能力 | 统一错误、超时重试、日志与指标、token 成本 |
| 对照结论 | 每个模块留下「Spring AI 与 LangChain4j 做法差异」的记录 |

## 明确不做

- **不复刻 star 的业务系统**：用户、权限、会话表、前端页面、中断/续跑状态机都不在本项目默认范围内。
- **不追求生产可用**：单机、单用户、无鉴权、无多租户、无高可用；这些能力只有在某个里程碑明确需要时才做。
- **不为 Spring AI 自研底层适配器**：优先使用官方 starter / 自动装配。只有当官方方式在当前版本或当前场景下不成立时，才自研，并把理由写进模块文档。
- **不把实验代码直接搬进 star 项目**：两边通过文档对照，而不是共享实现。

## 与 star-knowledge-assistant 的关系

| | star-knowledge-assistant | Polaris |
|---|---|---|
| 框架 | LangChain4j 1.20.0 | Spring AI 2.0.2 |
| 定位 | 业务向、深水区、可演示 | 实验向、生态对照、可复用结论 |
| 端口 | 8102 | 8103 |
| 状态机 / 中断续跑 | 自研并已落地 | 暂不纳入默认范围 |
| 文档 | `knowledge/` + `frontend/` | `docs/`（本目录） |

**判断标准**：Polaris 的产出首先是**结论文档**，其次才是代码。代码用来验证结论，不追求功能数量。

## 约束条件

- 单人开发、本机 Windows、本地 Maven；构建与测试必须能在一台机器上重复。
- 模型走 **DeepSeek 官方 API**（OpenAI 兼容协议）；API key 只通过环境变量注入，绝不进仓库。
- 端口固定 `8103`，上下文路径 `/api`；与 8101（salary-leap）、8102（star）错开。
- 所有「没实测过的数字或结论」必须标注 **待验证**，并写清楚验证方法。
