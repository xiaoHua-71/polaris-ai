# JDK 21 语言特性与项目用法

> 版本前提：JDK 21.0.5，`pom.xml` 中 `<java.version>21</java.version>`。快照时间：2026-11-17。
> 状态：✅ 当前代码已按本文描述使用；`mvn test` 通过（JDK 21.0.5）。

## ⓪ 先厘清：项目里的「新语法」不全是 JDK 21 才有的

`pom.xml` 声明以 JDK 21 编译，但不等于源码用到了 21 的全部新特性。按「特性在哪一版转正」拆开看：

| 特性 | 转正版本 | 项目是否使用 | 使用位置 |
|---|---|---|---|
| switch 表达式（箭头、返回值、枚举穷尽） | Java 14 | ✅ | `JdbcChatMemoryRepository.toMessage` |
| 文本块 `"""` | Java 15 | ✅（仅测试） | `JdbcChatMemoryRepositoryTests` 的建表 SQL |
| `CharSequence.isEmpty()` | Java 15 | ✅ | `TraceAdvisor.summarizeMessages` 的 `StringBuilder` |
| `record` | Java 16 | ✅ | 请求/响应 DTO、`ExtractedPerson`、SSE 事件 |
| `Stream.toList()` | Java 16 | ✅ | `ToolRegistry`、`JdbcChatMemoryRepository` |
| `sealed interface` | Java 17 | ✅ | `ChatStreamEvent` |
| 模式匹配 for switch | Java 21 | ✅ | `ChatController.eventName` |
| record 模式 | Java 21 | ✅ | `ChatController.eventName` |
| `SequencedCollection`（`getFirst`/`getLast`） | Java 21 | ✅（仅测试） | 消息列表与流式响应断言 |
| 虚拟线程 | Java 21 | ❌ | 见 ⑦ |
| 未命名变量/模式 `_` | 21 预览，22 转正 | ❌ | 见 ⑦ |
| 字符串模板 `STR."..."` | 21 预览，后续移除 | ❌ | 见 ⑦ |

**结论**：项目真正用到的 JDK 21 独占能力只有三块——**模式匹配 switch + record 模式**、**SequencedCollection**，以及作为其前提的 **sealed interface（17）** 和 **record（16）**。其余「现代写法」都是 14–16 时代的能力。

本文的目的不是罗列 API，而是记录两个问题：

1. 这些特性在项目里**具体解决了什么问题**；
2. 哪些特性**看起来适合、实际不能或不该用**，为什么。

## ① 模式匹配 switch + record 模式（Java 21）

### 用法

```java
sealed interface Shape permits Circle, Square {}
record Circle(double radius) implements Shape {}
record Square(double side) implements Shape {}

double area = switch (shape) {
    case Circle(double r) -> Math.PI * r * r;   // record 模式：直接解构出 r
    case Square(double s) -> s * s;
};                                              // sealed 类型不需要 default
```

两个能力经常一起出现：

- **模式匹配 for switch**（JEP 441）：`case` 后面可以写类型模式，不必先 `instanceof` 再强转；
- **record 模式**（JEP 440）：在类型模式基础上继续解构 record 的分量，`Circle(double r)` 直接拿到 `radius`。

对 `sealed` 类型，编译器知道所有子类型，因此：

- 不需要 `default`；
- 少写一个分支会**编译失败**（穷尽性检查）。

### 项目中的使用

`ChatStreamEvent` 是封闭的三种事件，`ChatController.eventName` 用模式匹配 switch 把「事件类型」映射成「SSE 事件名」：

```java
// ChatStreamEvent.java
public sealed interface ChatStreamEvent
        permits ChatStreamEvent.Delta, ChatStreamEvent.Done, ChatStreamEvent.Error {

    record Delta(String content) implements ChatStreamEvent {}
    record Done(String conversationId) implements ChatStreamEvent {}
    record Error(String message) implements ChatStreamEvent {}
}
```

```java
// ChatController.java:100
static String eventName(ChatStreamEvent event) {
    return switch (event) {
        case ChatStreamEvent.Delta(String content) -> "delta";
        case ChatStreamEvent.Done(String conversationId) -> "done";
        case ChatStreamEvent.Error(String message) -> "error";
    };
}
```

`send()` 现在只接收 `ChatStreamEvent`，事件名由 `eventName()` 推导，负载直接序列化同一个对象：

```java
// ChatController.java:108
private void send(SseEmitter emitter, Disposable.Swap subscription, ChatStreamEvent event) {
    emitter.send(SseEmitter.event()
            .name(eventName(event))
            .data(objectMapper.writeValueAsString(event), MediaType.APPLICATION_JSON));
}
```

测试覆盖了两点：

- `ChatControllerStreamTests.mapsStreamEventTypesToSseEventNames`：三种事件映射到 `delta` / `done` / `error`；
- `ChatControllerStreamTests.serializesStreamEventPayloadAsJson`：JSON 负载仍是 `{"content":...}`、`{"conversationId":...}`、`{"message":...}`，前端 SSE 契约不变。

### 好处

1. **穷尽性由编译器保证**：新增一种事件类型而忘记处理，`eventName` 直接编译失败。
2. **事件名与负载不会再错配**：改造前 `send(emitter, subscription, "delta", new Delta(token))` 的名字和负载是两个独立参数，复制粘贴时可能写成 `"done"` 配 `Delta`。现在名字从类型推导，只有单一事实来源。
3. **没有 `instanceof` + 强转**：分支里直接使用解构出的分量，少一层样板代码。

### 为什么这样写

SSE 的事件契约本来就是**封闭集合**：`delta`（片段）、`done`（结束）、`error`（失败）。封闭集合用 `sealed` 表达，把「只有这三种」写进类型系统，而不是只写在文档里。

事件名也从「调用方手工传参」改成「类型到名字的映射」，把契约集中在一个 `switch` 里，后续改协议时只有一个地方要动。

### 别的写法为什么不行

- **`instanceof` 链**：能工作，但没有穷尽性检查，新增事件类型不会编译失败；事件名仍要手工传，错配风险还在。
- **一个 record 加 `type` 字段**：
  ```java
  record ChatStreamEvent(String type, String content, String conversationId, String message) {}
  ```
  这样会出现非法状态：`type=delta` 却带着 `conversationId` 和 `message`；序列化还会输出一堆没用的 `null` 字段。当前「每个变体只带自己的字段」让非法状态不可表示。
- **用 `_` 丢弃未使用的模式变量**：`case ChatStreamEvent.Delta(_) ->` 看起来最干净，但**未命名变量在 JDK 21 是预览特性**（JEP 456，JDK 22 才转正），编译和运行都需要 `--enable-preview`。项目没有开启预览特性，所以只能写成 `case ChatStreamEvent.Delta(String content)`，即使 `content` 在分支里没用到。详见 ⑦。
- **嵌套 record 模式**：`case Wrapper(Inner(String x))` 这类写法项目里用不上，因为事件 record 没有嵌套 record 分量。

## ② sealed interface（Java 17）

### 用法

```java
public sealed interface Payment permits CardPayment, CashPayment {}
public record CardPayment(String cardNo) implements Payment {}
public record CashPayment() implements Payment {}
```

`permits` 列出全部实现；子类型必须满足 `final` / `sealed` / `non-sealed` 之一。所有实现都在同一个文件里时，`permits` 可以省略，但显式写出更能表达「这是一个封闭集合」。

### 项目中的使用

只用在 `ChatStreamEvent`（`ChatStreamEvent.java:3`）。三个实现都是嵌套 record，且都在同一文件中，`permits` 显式列全。

### 好处

- 对调用方承诺：这个接口不会在别处被随意扩展，因此可以安全地用穷尽 switch。
- 对维护者提示：新增子类型必须回到 `permits` 和所有 switch 处处理，编译器会提醒。

### 为什么这里要用

SSE 协议的事件集合由后端定义、前端消费，是一个天然的闭集。把它建模成 `sealed`，协议变更的影响面在编译期就能暴露。

### 为什么别处不用

- `ChatRequest`、`ChatResponse`、`ExtractRequest`、`ExtractedPerson` 都是**独立的 DTO**，没有子类型、没有多态分发，加 `sealed` 只会增加噪音。
- Spring AI 的 `Message` / `UserMessage` / `AssistantMessage` 是**框架提供的类**，不是本项目能修改的类型，无法 `sealed`（也不应该）。
- `sealed` 的价值在「需要穷尽分发」时才成立；只有单一实现或没有分支逻辑的类型不需要它。

## ③ record（Java 16）

### 用法

```java
public record ChatRequest(String message, String conversationId) {}
```

编译器生成：

- 全参规范构造器；
- 每个分量的访问器（`message()`、`conversationId()`）；
- `equals` / `hashCode` / `toString`；
- 类型是 `final`，分量是 `private final`，天然不可变。

需要校验时用**紧凑构造器**：

```java
public record Page(int size) {
    public Page {
        if (size <= 0) {
            throw new IllegalArgumentException("size 必须大于 0");
        }
    }
}
```

### 项目中的使用

| record | 用途 |
|---|---|
| `ChatRequest(String message, String conversationId)` | 同步/流式对话请求体，Spring MVC 反序列化 |
| `ChatResponse(String content)` | 同步对话响应体，Jackson 序列化 |
| `ExtractRequest(String message)` | 结构化抽取请求体 |
| `ExtractedPerson(String name, Integer age, String city, String occupation)` | 结构化抽取结果；`BeanOutputConverter` 按分量生成 JSON Schema 并反序列化 |
| `ChatStreamEvent.Delta/Done/Error` | SSE 事件负载 |

`ExtractedPerson` 还带了一个 `hasNoContent()` 业务方法：record 可以有实例方法，只是不能声明额外实例字段。

### 好处

- **DTO 只需要一行**：没有 getter/setter/构造器/`equals` 样板代码。
- **不可变**：请求/响应和事件在链路里传递时不会被意外修改。
- **字段名即契约**：`record` 分量名直接决定 JSON 字段名（Jackson）和结构化输出的 Schema 字段名，减少「字段叫 `userName` 还是 `username`」这类不一致。
- **值语义**：`equals`/`hashCode` 按分量比较，测试和集合操作符合直觉。

### 为什么这样写

这些类型都是**纯数据载体**：没有身份、没有生命周期、没有继承关系。这正是 record 的适用场景。

`ExtractedPerson` 用 `Integer` 而不是 `int`，因为模型可能没有抽取到年龄，`null` 表示「缺失」；record 允许包装类型分量。

### 为什么别的地方不用

- **Spring AI 的 `Message` 体系**：`UserMessage`、`AssistantMessage` 是框架类，很多地方按类继承扩展；我们不能也不应该把它们改成 record。
- **需要可变状态或代理的类型**：例如 JPA 实体（需要无参构造、可变字段、代理子类），record 都不满足。本项目用 `JdbcTemplate`，没有 JPA 实体，所以暂时不涉及。
- **事件的外层**：`ChatStreamEvent` 需要表达「多个变体」，所以外层是 `sealed interface`，record 只作为各变体。record 不能继承类，也不适合承担「封闭集合」的角色。
- **不要为了少写代码把有行为的类硬改成 record**：record 适合数据，不适合有复杂生命周期和可变状态的对象。

## ④ SequencedCollection（Java 21）

### 用法

JDK 21 给 `List`、`Deque`、`LinkedHashSet`、`LinkedHashMap` 的有序视图统一了「首尾访问」API：

```java
List<String> list = List.of("a", "b", "c");

list.getFirst();       // "a"
list.getLast();        // "c"
list.reversed();       // 逆序视图，不复制
list.addFirst("x");    // 仅可变 List 支持
list.addLast("z");
```

关键点：

- `List` 直接继承 `SequencedCollection`，所以**任何 List** 都能用 `getFirst()` / `getLast()` / `reversed()`；
- `Stream.toList()` 返回的不可变 List、`List.of(...)` 的结果同样支持读取端的这些方法；
- 写入端方法（`addFirst` 等）在不可变集合上会抛 `UnsupportedOperationException`。

### 项目中的使用

项目里没有自己实现「取最近 N 条」的裁剪逻辑，窗口裁剪在 Spring AI 的 `MessageWindowChatMemory` 内部完成。真正存在首尾访问的，是测试里对有序消息列表的断言：

```java
// JdbcChatMemoryRepositoryTests
assertThat(messages.getFirst().getMessageType()).isEqualTo(MessageType.USER);
assertThat(messages.getLast().getMessageType()).isEqualTo(MessageType.ASSISTANT);
Message message = repository.findByConversationId("c1").getFirst();

// PromptTraceAdvisorTests
assertThat(actual.getFirst()...getText()).isEqualTo("你");
assertThat(actual.getLast()...getText()).isEqualTo("好");
```

`TraceAdvisorTests` 的流式响应有 3 个元素，断言的是第 1、2 个，因此只把第一个改成 `getFirst()`，中间元素保留 `get(1)`——`getLast()` 在这里会指向第 3 个元素，语义就错了。

### 好处

- **意图更清楚**：`getFirst()` / `getLast()` 直接表达「取头/取尾」，不用读代码的人去确认 `0` 是头还是尾。
- **少算下标**：不需要 `size() - 1`，也就没有空列表时 `-1` 越界的推导负担。
- **统一 API**：List、Deque、LinkedHashSet 的首尾访问写法一致，切换集合类型时断言不用改。

### 为什么只在测试里用

- 生产代码里的「最近 N 条」由 Spring AI 的 `MessageWindowChatMemory` 实现。它不仅是简单截断，还要保证窗口从完整的一轮用户消息开始（`MessageWindowChatMemoryTests` 验证了这一点）。自己重写会重复框架逻辑，且更容易破坏 `ASSISTANT(tool_calls)` / `TOOL` 的消息配对。
- 项目自己的 `JdbcChatMemoryRepository` 只负责「按 id 顺序读出全部消息」，没有首尾裁剪；返回的 `List` 已天然支持 `getFirst()` / `getLast()`，只是当前没有调用点。

### 别的写法为什么不行

- **用 `get(0)` / `get(size() - 1)`**：能工作，但意图弱、易算错；这正是 `SequencedCollection` 想消除的样板代码。
- **自己包一层窗口裁剪以「用上」SequencedCollection**：属于为特性而特性。窗口语义（完整轮次、消息配对、最大条数）已经有经过测试的框架实现，重写的收益是负的。
- **`reversed()` 用得更多一点？** 目前没有反向遍历消息的需求，所以不用。等真的出现「从最新一条往前找」的逻辑时再引入。

## ⑤ switch 表达式（Java 14）

### 用法

```java
// 旧写法：语句 + break + 可能 fallthrough
String label;
switch (type) {
    case USER:
        label = "用户";
        break;
    case ASSISTANT:
        label = "助手";
        break;
    default:
        label = "未知";
}

// 新写法：表达式 + 箭头 + 无 fallthrough
String label = switch (type) {
    case USER -> "用户";
    case ASSISTANT -> "助手";
    case SYSTEM -> "系统";
    case TOOL -> "工具";
};
```

对枚举，分支覆盖全部常量时不需要 `default`，编译器会检查穷尽性。

### 项目中的使用

`JdbcChatMemoryRepository.toMessage`（`JdbcChatMemoryRepository.java:70`）把数据库里的 `message_type` 还原成 Spring AI 的消息对象：

```java
static Message toMessage(String type, String content) {
    MessageType messageType = MessageType.valueOf(type);
    return switch (messageType) {
        case USER -> new UserMessage(content);
        case ASSISTANT -> new AssistantMessage(content);
        case SYSTEM -> new SystemMessage(content);
        case TOOL -> throw new IllegalStateException("工具消息暂不支持持久化，M5 再实现");
    };
}
```

### 好处

- **switch 产生值**，可以直接 `return`，少一个临时变量；
- **没有 fallthrough**：箭头分支不会意外掉到下一个 `case`；
- **枚举穷尽检查**：`MessageType` 新增常量时，这里会编译失败而不是静默走到默认分支。

### 为什么这样写

数据库存的是 `MessageType.name()`，读出来先 `valueOf` 还原成枚举，再按枚举分支构造具体消息类。枚举是唯一事实来源，分支与 `MessageType` 的常量一一对应。

### 别的写法为什么不行

- **直接 switch 字符串常量**（Java 21 也支持）：
  ```java
  return switch (type) {
      case "USER" -> new UserMessage(content);
      case "ASSISTANT" -> new AssistantMessage(content);
      // ...
      case null, default -> throw new IllegalArgumentException("未知消息类型：" + type);
  };
  ```
  看起来更「Java 21」，但有两个代价：
  1. 引入魔法字符串，`USER` 和 `MessageType.USER.name()` 是两处需要同步的事实来源；
  2. 失去枚举的编译期穷尽检查——Spring AI 升级新增消息类型时，编译器不会提醒，只会在运行时抛异常。
- **`record` 模式**：这里不适用。入参是 `String` + `String`，返回的消息类是 Spring AI 的普通类，不是 record，没有可解构的分量。
- **`case null` 分支**：`message_type` 是 `NOT NULL` 列，且只由本项目写入；`null` 代表数据损坏，应当快速失败（`valueOf` 抛异常），而不是当成一个正常业务分支去兼容。给不可能发生的输入加分支，会掩盖真正的问题。

## ⑥ 其他已用的小特性

这些不是 JDK 21 新增，但属于项目当前使用的「现代 Java」写法，一并记录取舍：

| 特性 | 版本 | 用法 | 项目位置 | 为什么用 / 为什么没扩大使用 |
|---|---|---|---|---|
| 文本块 `"""` | 15 | 多行字符串字面量 | `JdbcChatMemoryRepositoryTests` 建表 SQL | 多行 DDL 可读性好。运行时 SQL 都是单行 + 占位符，用文本块反而增加缩进噪音 |
| `Stream.toList()` | 16 | `stream.toList()` | `ToolRegistry`、`JdbcChatMemoryRepository`、多处测试 | 比 `collect(Collectors.toList())` 短，返回不可变 List，符合只读返回值的语义。注意它不接受 `null` 元素 |
| `CharSequence.isEmpty()` | 15 | `summary.isEmpty()` | `TraceAdvisor.summarizeMessages` | `StringBuilder` 直接判空，避免 `length() == 0` 或先 `toString()` 再判空 |
| `String.strip()` / `isBlank()` | 11 | 去除首尾空白、判空白 | `TraceAdvisor.preview` / `hasText` | `strip()` 按 Unicode 空白处理，比 `trim()` 更符合「用户输入」的语义 |
| `List.of` / `Map.of` | 9 | 不可变小集合 | 控制器与测试 | 一行构造、不可变；不接受 `null` 元素，正好用于确定性数据 |
| `var` | 10 | 局部变量类型推断 | **未使用** | 项目统一写显式类型。不是禁止，只是当前代码里 DTO、流式管道的类型本身就是文档的一部分，暂未发现必须用 `var` 的场景 |

## ⑦ 没有使用 / 当前不能用的 JDK 21 特性

### 虚拟线程（JEP 444）

**用法**：

```java
Thread.startVirtualThread(() -> doWork());

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> doWork());
}
```

Spring Boot 也可以用一个开关让 Tomcat 使用虚拟线程：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

**项目为什么没用**：

1. 当前是 **Servlet MVC + `SseEmitter`**：`/chat` 的阻塞模型调用占用 Servlet 工作线程；`/chat/stream` 返回 `SseEmitter` 后由 Reactor 订阅推进，请求线程已经释放。开启虚拟线程会改变请求线程模型，但不改变模型调用的延迟与背压本质。
2. **SSE 的取消与回调需要重新验证**：`Disposable.Swap`、`emitter.onCompletion/onTimeout/onError` 与线程模型相关，换线程模型后要重新测「客户端断开 → 上游取消」。
3. **没有并发压测数据**：`06-风险与待验证.md` 明确写了「两条路径都没有并发压测，不能声称性能可接受」。在没有测量的情况下打开虚拟线程，只是把「未验证」换了个说法。
4. 这不是「不能用」，而是**当前证据不足**。合理的顺序是先做并发压测（M8 工程化阶段），再决定是否开启。

### 未命名变量 / 未命名模式 `_`（JEP 456）

**用法**：

```java
case ChatStreamEvent.Delta(_) -> "delta";   // 不关心分量内容
catch (Exception _) { }                      // 不关心异常对象
for (var _ : list) { }                       // 不关心元素
```

**当前为什么不能用**：该特性在 **JDK 21 是预览特性**，编译和运行都需要 `--enable-preview`；JDK 22 才转正。项目的 `pom.xml` 没有开启预览，因此：

- `ChatController.eventName` 只能写成 `case ChatStreamEvent.Delta(String content)`，即使 `content` 没用到；
- 想用 `_`，要么升级到 JDK 22+，要么给整个构建加 `--enable-preview`。后者会影响所有代码的编译与运行，风险和收益不成比例。

### 字符串模板 `STR."..."`（JEP 430）

**用法**：

```java
String message = STR."用户 \{name} 的年龄是 \{age}";
```

**为什么不用**：

1. JDK 21 中是**预览特性**，同样需要 `--enable-preview`；
2. 该特性后续被从 Java 中移除，属于「学了可能马上作废」的 API；
3. 项目的模板需求分两类，已有更合适的工具：
   - **提示词模板**：用 Spring AI 的 `StTemplateRenderer`，运行期从 `Resource` 渲染 `<text>` / `<format>` 等占位符；
   - **日志与错误信息**：用 SLF4J 的 `{}` 占位符或普通字符串拼接，不构造大段字符串。

### `case null` 与带 guard 的模式

**用法**：

```java
return switch (value) {
    case null -> "空";
    case String s when s.isBlank() -> "空白";
    case String s -> s;
    default -> "其他";
};
```

**为什么不用**：

- 项目内部的数据路径没有「有业务含义的 null 分支」：`message_type` 来自 `NOT NULL` 列；请求体字段在 Controller 边界统一校验。给内部不可能为 `null` 的值加分支，会掩盖数据损坏。
- guard（`when`）适合「同一类型按条件再分」的逻辑；当前的分支都是按类型/枚举直接映射，没有额外的布尔条件。

### 嵌套 record 模式

**用法**：

```java
record Order(Customer customer, Item item) {}
record Customer(String name, int age) {}

String name = switch (order) {
    case Order(Customer(String name, int age), Item item) -> name;
};
```

**为什么不用**：项目里的 record 都是扁平结构（DTO、事件负载），没有「record 里再套 record」的模型，因此没有可解构的嵌套分量。

### 模式匹配 for `instanceof`

**用法**：

```java
if (obj instanceof String s && s.length() > 3) {
    return s.toUpperCase();
}
```

**为什么不用**：主代码里没有「`instanceof` 后强转」的场景。Spring AI 的 `Message` 体系通过接口方法（如 `getText()`、`getMessageType()`）访问，不需要先判断具体子类；需要按类型分发的地方（SSE 事件）已经用 switch 模式匹配处理，不需要再写 `instanceof`。

## ⑧ 维护约定

1. **新增语言特性时，先回答三个问题**：
   - 它是否消除了一个非法状态，或让编译器多抓一类错误？
   - 它是否让代码更短且不牺牲可读性？
   - 如果不用它，代价是什么？
   三个都答不上来，就不要为了「用上新特性」而改。
2. **预览特性默认不引入**。确需使用时，必须在本文记录：为什么值得开启 `--enable-preview`、影响哪些构建/运行环节、升级路径是什么。
3. **表格与代码同步**。本文的「使用位置」是快照；重构后如果特性被移除或迁移，更新本文，不要留下过期结论（过期文档比没有文档更糟）。
4. **验证命令**：

   ```bash
   JAVA_HOME="E:/Java/jdk-21.0.5" mvn test
   ```

   本机默认 JDK 是 11，直接跑 `mvn` 会报「不支持发行版本 21」。需要显式指定 JDK 21（见 `02-技术栈与版本.md`）。
