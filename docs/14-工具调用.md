# 工具调用（M5）

> 版本前提：Spring AI 2.0.2 + Spring Boot 4.1.2。快照时间：2026-11-16。
> 状态：✅ 2026-11-16 完成（DeepSeek 实测；未覆盖项见 ⑤）。

## ⓪ 先看懂几个词（零基础可读，已懂可跳过）

### 工具调用是什么

模型本身只会「生成文本」，不会查时间、算数、读数据库。**工具调用**（tool calling / function calling）是：

1. 服务端把若干「工具说明书」随请求发给模型；
2. 模型认为需要时，不直接回答，而是返回「我要调用 `getCurrentTime`，参数是 `Asia/Shanghai`」；
3. 服务端真正执行这个函数，把结果作为一条消息发回给模型；
4. 模型基于工具结果生成最终回答。

模型负责**决策**，服务端负责**执行**。模型永远不直接执行代码。

### 工具循环

上面第 2–4 步可能重复多次：模型看到结果后可能再调另一个工具。整个「调用模型 → 执行工具 → 再调用模型」的过程叫**工具循环**。

本项目里这个循环由框架的 `ToolCallingAdvisor` 驱动，不是控制器里手写的 `while`。

### 工具 Schema 与工具定义

模型怎么知道有哪些工具、参数叫什么？靠**工具定义**（`ToolDefinition`）：

- 名称、描述；
- 参数的 JSON Schema（类型、是否必填、说明）。

这些信息会占 prompt token。工具越多、描述越长，每次调用的基础成本越高。

### 轮次护栏（limits）

工具循环不设上限时，模型可能反复调用工具，烧 token、拖长响应，甚至死循环。**轮次护栏**限制：

- 单个工具最多调几次；
- 一轮对话总共最多调几次；
- 超限时是抛异常（`THROW`）还是把错误作为工具结果回给模型（`RETURN_ERROR_RESPONSE`）。

### 结果截断

工具可能返回很长的文本（网页、日志、查询结果）。整段塞回模型会撑爆上下文、增加成本。**结果截断**在工具结果进入 prompt 前砍到固定长度。

### 消息配对

工具调用会产生 `ASSISTANT(tool_calls)` 与 `TOOL(result)` 两类消息，它们必须成对出现。记忆裁剪或持久化如果只保留一半，后续请求可能被 provider 拒绝。M2 的记忆仓库当前只支持 USER / ASSISTANT / SYSTEM，这是 M5 必须验证的边界。

## ① 这个模块治的是哪类病

模型的知识被训练数据冻结，也无法安全地执行副作用。工具调用要解决的是：

- **能力扩展**：让模型能获取实时信息（时间）、执行确定性计算，而不是编造。
- **执行边界**：模型只提议调用，真正执行在后端，参数与副作用可控。
- **循环治理**：谁驱动循环、最多几轮、超限怎么办。
- **失败隔离**：工具抛异常时，是拖垮整个对话，还是把错误告诉模型让它继续。
- **成本治理**：工具 Schema 与工具结果都会进入 prompt，必须有上限。

典型失败模式：

1. **死循环**：模型反复调用同一工具，请求永不结束。
2. **参数幻觉**：模型给出不存在的时区、非法表达式，工具直接抛异常。
3. **工具异常炸链路**：工具一个 `NullPointerException` 让整个 HTTP 请求 500。
4. **结果撑爆上下文**：工具返回大段文本，下一次模型调用超 token。
5. **消息配对断裂**：记忆里只剩 `TOOL` 没有对应的 `ASSISTANT(tool_calls)`，provider 报错。
6. **越权执行**：把任意 SQL / 命令包装成工具，模型可以诱导执行。

## ② Spring AI 官方怎么做

**版本：Spring AI 2.0.2。** 以下类名与默认值均从本地依赖 jar 确认。

### 定义与注册

- 注解 `org.springframework.ai.tool.annotation.Tool`：`name`、`description`、`returnDirect`、`resultConverter`。
  - `returnDirect=true` 时工具结果直接作为最终回答，不再回模型；本项目不使用。
  - `resultConverter` 默认 `DefaultToolCallResultConverter`，把返回值序列化成字符串。
- 注解 `org.springframework.ai.tool.annotation.ToolParam`：`description`、`required`（默认 true）。
- 注册方式：
  - `ChatClient.Builder#defaultTools(Object...)`：传普通对象，框架扫描 `@Tool` 方法；
  - `ChatClient.Builder#defaultToolCallbacks(ToolCallback...)`：直接注册回调，适合包装 / 动态生成；
  - `MethodToolCallbackProvider.builder().toolObjects(...).build().getToolCallbacks()`：手动生成回调数组。
- `ToolCallback` 接口：`getToolDefinition()`、`call(String)`、`call(String, ToolContext)`。自定义包装只需实现这层。

### 循环归属

- `ToolCallingAdvisor`（`spring-ai-client-chat`）负责整个工具循环，**默认由自动装配注册**（`spring.ai.chat.client.tool-calling.enabled=true` 是默认值，已从字节码确认）。
- 默认 order = `HIGHEST_PRECEDENCE + 300`。本项目现有链条：
  - `TraceAdvisor`（+150）→ `MessageChatMemoryAdvisor`（+200）→ `PromptTraceAdvisor`（+250）→ `ToolCallingAdvisor`（+300）→ 模型。
  - 含义：记忆注入发生在工具循环之前；`PromptTraceAdvisor` 只记录**首轮** prompt；`TraceAdvisor` 包住整个循环，耗时 / token 是总账。
- 执行由 `ToolCallingManager`（默认 `DefaultToolCallingManager`）完成。

### 轮次护栏（内置）

`spring.ai.tools` 前缀，自动装配到 `ToolCallingManager`：

| 配置 | 说明 |
|---|---|
| `spring.ai.tools.limits.max-calls-per-tool-default` | 每个工具的默认调用上限 |
| `spring.ai.tools.limits.max-calls-per-tool.<toolName>` | 单工具覆盖 |
| `spring.ai.tools.limits.max-total-tool-calls` | 一轮对话的工具调用总数上限 |
| `spring.ai.tools.limits.excluded-tools` | 不受限制的工具 |
| `spring.ai.tools.limits.on-limit-exceeded` | `THROW` 或 `RETURN_ERROR_RESPONSE` |

- 未配置时上限为 `NO_LIMIT = -1`（不限），**必须显式配置**。
- `THROW`：抛 `ToolCallLimitExceededException`，请求失败。
- `RETURN_ERROR_RESPONSE`：把「超限」作为工具错误结果回给模型，模型可以据此收尾。

### 工具异常

- 默认 `DefaultToolExecutionExceptionProcessor`：`alwaysThrow=false`，把异常转成错误文本作为工具结果返回，模型继续生成回答。
- 配置项 `spring.ai.tools.throw-exception-on-error`（默认 false）可改为直接抛出。

### 结果截断

2.0.2 的 tool 相关包里**没有**内置的结果截断配置（已检索类清单与常量）。如需上限，要自己包装 `ToolCallback`。

## ③ 本项目为什么这么落地

| 决定 | 做法 | 备选 | 理由 |
|---|---|---|---|
| 工具挂在哪个 client | 新增 `toolChatClient`（带记忆 + 工具），接口 `POST /api/chat/tools` | 直接给现有 `chatClient` 加工具 | 保持 M1–M4 的 `/chat` 行为可回归；工具 Schema 有 token 开销，不该无条件影响所有对话。 |
| 工具注册方式 | 自定义 `@ToolGroup` 注解 + `ToolRegistry`：工具类加注解即为 Spring Bean，启动时按分组收集并统一截断 | 在 `ToolConfig` 里逐个 `@Bean` 再手动传入 Provider | 新增工具只改工具类，不改装配代码。 |
| 上下文控量 | `polaris.tools.groups` 按分组装配，只把当前场景需要的工具定义发给模型 | 全量注册所有工具 | 工具定义常驻 prompt，数量增长时是主要固定成本；分组是最直接、零额外模型调用的控制手段。 |
| 工具数量与类型 | 两个只读工具：`getCurrentTime`、`calculate` | 写操作工具 / 数据库查询 | 只读工具无副作用，失败成本低；时间与计算都能给出确定性、可人工核对的结果。 |
| 计算实现 | SpEL `SimpleEvaluationContext` + 字符白名单 | 自写表达式解析器 / `ScriptEngine` | 自写解析器代码多；`ScriptEngine` 在 JDK 21 已无 Nashorn。`SimpleEvaluationContext` 禁止类型引用与方法调用，配合白名单足够安全。 |
| 结果截断 | 自定义 `TruncatingToolCallback`，上限 2000 字符 | 不截断 / 在各工具内截断 | 框架无内置能力；装饰器对工具透明，后续新增工具自动生效。 |
| 轮次护栏 | `max-calls-per-tool-default=3`、`max-total-tool-calls=5`、超限 `RETURN_ERROR_RESPONSE` | 不设限 / `THROW` | 不设限可能死循环；`THROW` 会让用户看到一个裸 500。错误回给模型更符合「可预期降级」。 |
| 工具异常 | 沿用默认处理（错误文本回给模型） | `throw-exception-on-error=true` | 单个工具参数错误不应拖垮整个对话；要验证的是「模型能否基于错误结果收尾」。 |
| 记忆 | `toolChatClient` 挂 `MessageChatMemoryAdvisor` | 不挂记忆 | 路线图要求验证工具调用与记忆的配合，必须实测消息配对与落库行为。 |

## ④ 数据结构与流程

### 接口

`POST /api/chat/tools`，请求体与 `/api/chat` 相同：

```json
{"message":"现在上海几点？顺便算一下 (12+3)*4。","conversationId":"22222222-2222-2222-2222-222222222222"}
```

响应：

```json
{"content":"上海现在是……；计算结果为 60。"}
```

- 参数校验与 `/chat` 一致：`message` 非空、`conversationId` 非空且 ≤64 字符 → 否则 400。
- 工具异常默认不改变 HTTP 状态：错误作为工具结果回给模型。
- 超限且配置为 `RETURN_ERROR_RESPONSE` 时同样不报错，由模型在回答中说明。
- 模型调用异常 → 框架默认 500（M8 统一）。

### 工具

| 工具名 | 分组 | 参数 | 返回 | 说明 |
|---|---|---|---|---|
| `getCurrentTime` | `time` | `zoneId`（可选，IANA 时区） | `yyyy-MM-dd HH:mm:ss XXX` | 空值默认 `Asia/Shanghai`；非法时区抛异常 |
| `calculate` | `calc` | `expression` | 数字字符串 | 只允许数字、括号、`+ - * /`、空格、小数点；长度 ≤200 |

### 注册与分组

- 工具类标注 `@ToolGroup(group = "time")`。该注解元注解为 `@Component`，类会被组件扫描注册为 Bean。
- `ToolRegistry` 启动时收集所有 `@ToolGroup` Bean，用 `MethodToolCallbackProvider` 生成回调，逐个包 `TruncatingToolCallback`（2000 字符），再按分组建索引。
- `ToolConfig` 只负责按 `polaris.tools.groups` 过滤并暴露一个 `ToolCallbackProvider`：留空加载全部分组；配置了未知分组会在启动时抛异常。
- 新增工具：新建类 + `@ToolGroup` + `@Tool` 方法即可，无需改 `ToolConfig`。
- 分组同时是上下文治理手段：只挂当前场景需要的分组，避免所有工具定义常驻 prompt。

### 流程

```text
1. 校验 message / conversationId              不合法 → 400
2. toolChatClient.prompt().user(message)
     .advisors(conversationId)                → 记忆注入历史
     .call().content()
3. ToolCallingAdvisor 驱动循环：
     a. 模型返回 tool_calls
     b. ToolCallingManager 检查 limits
     c. 执行 ToolCallback（结果经 TruncatingToolCallback 截断）
     d. 工具结果作为 TOOL 消息回给模型
     e. 重复 a–d，直到模型返回普通文本或触发上限
4. MessageChatMemoryAdvisor 保存本轮 USER / 最终 ASSISTANT
5. 返回 {"content": 最终回答}
```

### 配置

| 项 | 值 | 说明 |
|---|---|---|
| `spring.ai.tools.limits.max-calls-per-tool-default` | `3` | 单工具上限 |
| `spring.ai.tools.limits.max-total-tool-calls` | `5` | 单轮总上限 |
| `spring.ai.tools.limits.on-limit-exceeded` | `RETURN_ERROR_RESPONSE` | 超限降级 |
| `polaris.tools.groups` | 空（加载全部） | 逗号分隔的分组名；`TOOL_GROUPS` 环境变量可覆盖 |
| 工具结果上限 | 2000 字符 | `ToolRegistry` 常量，经 `TruncatingToolCallback` 截断 |
| 表达式长度上限 | 200 字符 | `CalculatorTools` 常量 |
| 工具调用开关 | 默认开启 | `spring.ai.chat.client.tool-calling.enabled` |

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- **写操作工具**：没有落库、发消息、执行命令类工具；`returnDirect` 也未使用。
- **人工确认**：副作用工具需要确认，当前阶段不引入（也没有副作用工具）。
- **ToolContext 透传**：未把用户身份 / 会话信息放进 `ToolContext`；工具无法按用户隔离。
- **工具级观测**：没有单独记录每次工具调用的参数、耗时、结果大小；只有整条链路的总耗时 / token。
- **工具结果缓存**：重复调用会重复执行。
- **工具按需检索**：仅实现启动时分组过滤；未实现 Tool Search / 意图路由，工具定义仍随所选分组全量进入 prompt。
- **流式工具接口**：`ToolCallingAdvisor` 支持流式，但本阶段只做同步 `/chat/tools`。
- **MCP 工具**：属于 M7。

### 坑

1. **现象**：工具定义明明注册了，模型却不调用。
   - 原因：描述太模糊、参数 schema 不清晰，或系统提示词没有「需要时用工具」的引导。
   - 规避：工具描述写清「什么时候用」；参数都给 `@ToolParam(description=...)`；系统提示词显式说明优先用工具而非猜测。

2. **现象**：配置了 `spring.ai.tools.limits.*` 但似乎不生效。
   - 原因：limits 由自动装配的 `ToolCallingManager` 读取；如果自定义了 `ToolCallingManager` Bean，自动配置会退让。
   - 规避：不自定义 Manager，直接用属性；需要定制时手动 `DefaultToolCallingManager.builder()` 并同步配置。

3. **现象**：工具异常导致对话中断。
   - 原因：把 `spring.ai.tools.throw-exception-on-error` 设为 true，或工具抛的是 `Error` / 无法处理的异常。
   - 规避：保持默认 false；工具内部只抛可预期的 `RuntimeException`。

4. **现象**：工具返回大段文本后下一次模型调用报 token 超限。
   - 原因：框架不截断工具结果。
   - 规避：新增工具只要标注 `@ToolGroup`，`ToolRegistry` 会统一包 `TruncatingToolCallback` 截断。

5. **现象**：担心记忆里出现 `TOOL` 消息导致 `JdbcChatMemoryRepository` 抛异常。
   - 原因：仓库当前显式拒绝 TOOL 类型，理论上需要扩展映射。
   - 规避：**2026-11-16 实测确认不会发生**：`MessageChatMemoryAdvisor` 只落 USER / 最终 ASSISTANT，工具中间消息不写库。若未来换成保留工具历史的记忆实现，需要重新检查。

### 实测记录（2026-11-16，deepseek-flash）

| 用例 | 结果 |
|---|---|
| 「现在上海几点了？」 | 200，回答时间与工具输出一致 |
| 「帮我算一下 (12+3)*4」 | 200，回答 60 |
| 混合：「纽约几点 + 年份乘 2」 | 200，两个工具结果都正确 |
| 同会话追问「我刚才问的是哪个城市的时间？」 | 200，正确回答上海；未再次调用工具 |
| 非法时区 `Not/AZone` | 工具异常降级为错误文本，HTTP 200，回答包含 `Unknown time-zone ID` |
| `1/0` | 工具异常降级，HTTP 200，回答包含 `/ by zero` |
| `max-total-tool-calls=1`（环境变量覆盖） | 第二个工具（并行发出）被拒，模型在回答中说明超限；HTTP 200 |
| 数据库记录 | 仅 USER / ASSISTANT，无 TOOL 消息 |
| 工具 Schema 的 token 开销 | 单次样本：≈1054–1086 prompt tokens；对话基线 ≈45。混合两轮累计 1703 |
| `/chat`、`/chat/extract` 回归 | 200 / 200 |
