# 结构化输出与提示词（M4）

> 版本前提：Spring AI 2.0.2 + Spring Boot 4.1.2。快照时间：2026-11-16。
> 状态：✅ 2026-11-16 完成（DeepSeek 实测；未覆盖项见 ⑤）。

## ⓪ 先看懂几个词（零基础可读，已懂可跳过）

这一节只解释读懂后文**绕不开**的概念，不涉及实现细节。

### 结构化输出是什么

普通对话返回一段自然语言。**结构化输出**要求模型返回**固定字段**的数据，反序列化成程序里的对象，例如：

```json
{"name":"张三","age":30,"city":"杭州","occupation":"工程师"}
```

这样下游代码可以直接 `person.age()`，不用解析自然语言。它和「让模型输出 JSON」的区别在于：**有明确的类型目标、有失败判定**。模型输出的 JSON 解析不了，就叫失败，不能当普通文本继续用。

### JSON Schema / 格式指令

模型不知道 Java 类长什么样。要让它输出固定字段，有两种常见做法：

- **格式指令（prompt 方式）**：在 prompt 里追加一段「请输出符合以下 JSON Schema 的 JSON」。模型照着写，服务端再解析。
- **原生结构化输出（provider 方式）**：请求里带 `response_format` / `output_schema` 等参数，由 provider 在解码阶段约束输出。是否支持、支持到什么程度，**取决于 provider 和模型**。

本项目 DeepSeek 走 OpenAI 兼容协议；它是否支持原生 `json_schema` 需要实测，不能默认可用。

### 提示词模板（prompt template）

把 prompt 从 Java 字符串里挪到独立文件，用占位符传参：

```text
从下面的文本中抽取人物信息：

<text>
```

`<text>` 是占位符（本项目把分隔符改成了 `<>`，原因见 ⑤）。模板的价值：

- prompt 改动不碰 Java 代码，diff 更干净；
- 同一模板可复用于不同输入；
- 避免 Java 字符串拼接导致的转义地狱。

### ST（StringTemplate）与分隔符

Spring AI 的默认模板渲染器是 StringTemplate（`StTemplateRenderer`），默认用 `{}` 表示占位符。问题在于：**JSON 也用 `{}`**。模板里一旦出现 JSON 示例（结构化输出几乎必然出现），`{}` 会被当成占位符解析，直接报错或渲染出空值。

规避方式：构建渲染器时把分隔符换成 `<>`，模板里写 `<text>`，JSON 里的 `{}` 原样保留。

### 解析前的文本清洗

模型经常「加戏」：

- 用 ` ```json ... ``` ` 包住 JSON；
- 先写一句「好的，结果如下：」；
- 思考型模型带上 `<thinking>...</thinking>`。

`BeanOutputConverter` 内部有 `CompositeResponseTextCleaner`（Markdown 代码块、thinking 标签、首尾空白），解析前先清洗。清洗解决「包裹层」，**不解决字段缺失、类型错误、编造内容**。

## ① 这个模块治的是哪类病

自由文本输出无法被程序稳定消费。结构化输出要解决的是：

- **可反序列化**：模型输出能稳定转成目标类型，而不是每次写个正则去抠字段。
- **失败可判定**：解析失败、字段缺失、类型不符时，有明确的错误路径，而不是把半个对象塞给下游。
- **提示词可维护**：prompt 与代码分离，修改、复用、对比有据可查。
- **与记忆/流式的关系**：结构化接口是否需要记忆？流式还能不能结构化？这些必须先定清楚。

它处在链路的**输出侧**：上游是模型调用，下游是业务代码。边界是「把模型文本变成类型安全的对象」，**不负责**：

- 校验业务语义（例如「年龄必须小于 150」是业务规则）；
- 保证内容真实（模型仍可能编造，只能通过提示词与抽检降低）；
- 统一错误响应（属于 M8）。

典型失败模式：

1. **裸文本当 JSON 用**：模型返回「抱歉，我无法提取」，下游 `readValue` 崩溃。
2. **Markdown 包裹**：` ```json ` 围栏没去掉，解析失败。
3. **字段漂移**：这次叫 `city`，下次叫 `城市`；schema 约束不住时尤其常见。
4. **编造缺失值**：文本里没有年龄，模型硬填一个 30。
5. **流式结构化幻觉**：以为流式每个 chunk 都是完整 JSON，实际上增量只是文本碎片。

## ② Spring AI 官方怎么做

**版本：Spring AI 2.0.2。** 以下类名均从本地依赖 jar 确认。

### 转换器

- `org.springframework.ai.converter.BeanOutputConverter<T>`（`spring-ai-model`）：
  - 构造：`new BeanOutputConverter<>(Class<T>)` 或 `ParameterizedTypeReference<T>`；
  - `getFormat()`：生成给模型看的格式指令；`getJsonSchema()` / `getJsonSchemaMap()`：生成 JSON Schema；
  - `convert(String)`：清洗 + 反序列化；
  - 使用 **Jackson 3**（`tools.jackson.databind.json.JsonMapper`），与本项目一致；
  - 可传入自定义 `JsonMapper` 与 `ResponseTextCleaner`。
- 同包还有 `ListOutputConverter`、`MapOutputConverter`，以及清洗器 `MarkdownCodeBlockCleaner`、`ThinkingTagCleaner`、`WhitespaceCleaner`。

### ChatClient 的入口

`ChatClient.CallResponseSpec`（同步）提供：

| 方法 | 用途 |
|---|---|
| `entity(Class<T>)` / `entity(ParameterizedTypeReference<T>)` | 调用模型并直接返回目标类型 |
| `entity(StructuredOutputConverter<T>)` | 自定义转换器 |
| `responseEntity(...)` | 同时拿到 `ChatResponse`（含 usage）与转换结果 |

`EntityParamSpec` 有两个可选开关：

- `useProviderStructuredOutput()`：走 provider 原生结构化输出（OpenAI 侧对应 `OpenAiChatOptions.Builder#outputSchema`）；
- `validateSchema()`：配合 `StructuredOutputValidationAdvisor` 做 schema 校验。

**边界**：

- `ChatClient.StreamResponseSpec` 在 2.0.2 **没有** `entity(...)`。结构化 + 流式不能直接组合，只能自行聚合完整文本后再 `BeanOutputConverter.convert()`。
- `StructuredOutputValidationAdvisor.builder().outputType(...).maxRepeatAttempts(n)` 能在校验失败时重试；**默认不启用**，`entity()` 本身不会自动重试。
- 原生结构化输出依赖 provider 支持。**2026-11-16 实测**：DeepSeek 直连端点对 `response_format={"type":"json_schema"}` 返回 HTTP 400（`This response_format type is unavailable now`）；`{"type":"json_object"}` 可用，但只保证「是合法 JSON 对象」，不校验 schema。因此「provider 原生 schema」在 DeepSeek 上当前不可用。

### 提示词模板

- `org.springframework.ai.chat.prompt.PromptTemplate`：`new PromptTemplate(Resource)` / `new PromptTemplate(String)`，`create(Map)` 生成 `Prompt`，`render(Map)` 只渲染文本。
- 渲染器接口 `org.springframework.ai.template.TemplateRenderer`；实现 `StTemplateRenderer`（`spring-ai-template-st`）。
  - **本项目依赖树里 `spring-ai-template-st` 已经存在**（经 `spring-ai-model` 传递引入），无需额外加依赖。
  - `StTemplateRenderer.builder().startDelimiterToken('<').endDelimiterToken('>')` 可换分隔符。
- 接入 `ChatClient` 的两种方式：
  - `ChatClient.Builder#defaultTemplateRenderer(...)`：客户端级默认渲染器；
  - `requestSpec.templateRenderer(...)`：单次请求覆盖。
- `PromptUserSpec.text(Resource)` + `param(...)` / `params(...)`：直接从 classpath 资源渲染 user 消息。

**边界**：模板机制只负责占位符替换，不做变量缺失之外的内容校验；分隔符冲突、模板语法错误在渲染期才暴露。

## ③ 本项目为什么这么落地

| 决定 | 做法 | 备选 | 理由 |
|---|---|---|---|
| 演示场景 | `POST /api/chat/extract`：从一段中文文本抽取人物信息 | 意图分类 / 情感分析 | 字段种类多（字符串、数字、可空），能覆盖类型转换与缺失值两类失败；结果肉眼可核对。 |
| 转换方式 | 手动 `BeanOutputConverter.convert(raw)` + `call().content()` | `ChatClient.entity(ExtractedPerson.class)`；`useProviderStructuredOutput()` 走原生 JSON Schema | `entity()` 内部同样使用 `BeanOutputConverter`，但转换失败时拿不到模型原始输出，而「非法输出」正是本模块要诊断的路径。手动转换可记录原始输出，并精确区分 `JacksonException`（→ 422）与模型调用异常（→ 500）。DeepSeek 对 `json_schema` 的支持未验证，格式指令方式对 provider 无要求。 |
| 格式指令注入 | 模板里留 `<format>` 占位符，传入 `converter.getFormat()` | 让 `entity()` 自动追加 | 手动转换必须自己注入格式指令；显式传参也能从 `PromptTraceAdvisor` 日志里看清最终 prompt。 |
| 失败处理 | 解析失败 → HTTP 422；输入非法 → 400；模型调用异常 → 框架默认 500 | 自动重试 / 用 repair prompt 再问一次 | 首次落地先让失败**可见**；自动重试会增加成本与延迟，且「重试仍失败」的路径同样要设计，留到 M8 统一策略时做。 |
| 记忆 | 结构化接口**不挂记忆**，独立 `structuredChatClient` | 复用对话 `chatClient` | 默认记忆 Advisor 在缺 `conversationId` 时会落到默认会话，抽取请求会污染对话历史；抽取本身是无状态任务，不需要上下文。 |
| 提示词管理 | `classpath:/prompts/*.st` 资源文件 + `StTemplateRenderer`（`<>` 分隔符） | 硬编码在 Java / 数据库管理 | 资源文件可版本化、可 diff、无额外基础设施；数据库管理属于后续运营需求，当前无证据需要。 |
| 分隔符 | `<` / `>` | 默认 `{}` | 模板里要放 JSON 示例，`{}` 会与 ST 语法冲突。 |
| 业务校验 | 转换成功后做最小校验：所有字段为空 → 422 | 不做任何校验 / 引入 Bean Validation | 防止模型返回空对象被当成成功；更细的业务规则（年龄范围等）不属于本模块。 |

## ④ 数据结构与流程

### 接口

`POST /api/chat/extract`

请求：

```json
{"message":"张三今年30岁，在杭州做后端工程师。"}
```

响应：

```json
{"name":"张三","age":30,"city":"杭州","occupation":"后端工程师"}
```

字段说明：

| 字段 | 类型 | 可空 | 说明 |
|---|---|---|---|
| `name` | string | 是 | 文本中明确出现的人名 |
| `age` | number | 是 | 明确出现的年龄（阿拉伯数字） |
| `city` | string | 是 | 明确出现的城市 |
| `occupation` | string | 是 | 明确出现的职业 |

- 缺失信息返回 `null`，**不允许编造**（写在提示词里，但无法强制）。
- 输入上限：`message` 非空且不超过 2000 字符（代码常量）；超限 → HTTP 400。
- 模型输出无法转换，或转换后所有字段为空 → HTTP 422。
- 模型调用异常（网络 / 401 / 超时）→ 当前仍是框架默认 500，M8 统一。

### 流程

```text
1. 校验 message                         不合法 → 400
2. structuredChatClient.prompt()
     .user(u -> u.text(prompts/extract-person.st)
                  .param("text", message)
                  .param("format", converter.getFormat()))
     .call()
     .content()                         // 拿到模型原始文本
3. converter.convert(raw)              // Jackson 3 反序列化
4. 转换成功 → 最小校验 → 返回 JSON
5. 转换抛 JacksonException → DEBUG 记录原始输出 → 422
```

### Advisor 组成

`structuredChatClient` 与对话用的 `chatClient` 是**两个 Bean**：

| Bean | Advisor | 记忆 |
|---|---|---|
| `chatClient` | `TraceAdvisor` → `MessageChatMemoryAdvisor` → `PromptTraceAdvisor` | 有（按 `conversationId`） |
| `structuredChatClient` | `TraceAdvisor` → `PromptTraceAdvisor` | 无 |

- `ChatClient.Builder` 由 Spring AI 自动装配为 **prototype** 作用域（2.0.2 已从字节码确认），每个 `@Bean` 方法拿到的是独立实例，不会互相污染默认配置。
- 可观测日志复用 M3 之后的外层 / 内层 Advisor，抽取请求同样能看到最终 prompt 与 token。

### 配置

| 项 | 值 | 说明 |
|---|---|---|
| 模板路径 | `classpath:/prompts/extract-person.st` | 资源文件，随 jar 发布 |
| 模板分隔符 | `<` / `>` | 渲染器级配置 |
| 输入上限 | 2000 字符 | 代码常量，暂未做成配置项 |
| 温度 | 沿用全局 `0.7` | 是否影响 schema 遵循度未单独验证 |

## ⑤ 边界、已知限制、踩过的坑

### 没做什么

- **流式结构化输出**：2.0.2 的 `StreamResponseSpec` 没有 `entity()`；当前未实现「聚合完整文本再转换」。若需要，应单独设计（何时转换、增量能否提前校验、失败如何通知客户端）。
- **原生结构化输出**：未使用 `useProviderStructuredOutput()`，未验证 DeepSeek 的 `json_schema` 支持。
- **自动重试 / 修复**：解析失败直接 422，不会用 repair prompt 再问一次，也不会自动重试。
- **提示词热更新**：模板打包在 jar 里，改动需重启。
- **字段级强约束**：未引入 Bean Validation；模型返回 `age=9999` 也会被接受（只做「全空 → 422」）。
- **统一错误响应**：422 的响应体仍是框架默认格式，不含具体原因；M8 处理。
- **多语言 / 多 schema**：只有一个人物抽取场景；未验证 schema 增多后的模板管理方式。

### 坑

1. **现象**：模板里写 JSON 示例后启动或渲染报模板语法错误。
   - 原因：ST 默认用 `{}` 作占位符，JSON 的花括号被当成表达式。
   - 规避：`StTemplateRenderer` 改用 `<` / `>` 分隔符；模板内只对真正的变量使用 `<>`。

2. **现象**：模型输出带 ` ```json ` 围栏或前置解释文字，反序列化失败。
   - 原因：模型把「输出 JSON」理解成「在回答里展示 JSON」。
   - 规避：`BeanOutputConverter` 内置清洗器处理常见包裹；提示词里明确要求「只输出 JSON，不要解释」。清洗器未覆盖的病态输出（JSON 中间夹注释）仍会失败 → 422。

3. **现象**：`entity()` 与 `stream()` 组合时编译不过。
   - 原因：`StreamResponseSpec` 在 2.0.2 没有 `entity()`。
   - 规避：同步 `call().entity(...)`；流式结构化另立方案，不硬拼。

4. **现象**：转换器报 Jackson 2 / Jackson 3 类型不匹配。
   - 原因：`BeanOutputConverter` 在 2.0.2 使用 Jackson 3（`tools.jackson.*`）；网上大量示例仍用 Jackson 2（`com.fasterxml.jackson.*`）。
   - 规避：以本地 jar 的方法签名为准；本项目全局注入 `tools.jackson.databind.ObjectMapper`。

5. **现象**：响应里多出一个 `"empty":false` 字段。
   - 原因：record 上定义了 `boolean isEmpty()`，Jackson 把 `isXxx()` 当成 getter，序列化出额外属性。
   - 规避：改名 `hasNoContent()`，并用序列化测试锁住「只输出声明字段」。

### 实测记录（2026-11-16，deepseek-flash）

| 用例 | 结果 |
|---|---|
| 完整信息：「张三今年30岁，在杭州做后端工程师。」 | 200，四个字段全部正确 |
| 稀疏信息：「李四昨天来过。」 | 200，仅 `name`，其余字段 `null`（未编造） |
| 中文数字年龄：「赵六今年三十五岁……」 | 200，`age=35`（模型做了归一化） |
| 无人物信息：「周末和朋友去爬山了。」 | 422（模型返回全 `null` 对象，被最小校验拦下） |
| 空 message / 超 2000 字符 | 400 / 400 |
| 连续 5 次抽取 | 解析失败 0 次；4 次成功 200，1 次按预期 422 |
| 抽取请求是否写记忆 | 未新增 `chat_message` 记录，`conversationId=-` |
| 格式指令 token 开销 | 单次样本：抽取 prompt ≈398–403 tokens；对话基线 ≈45 tokens（非性能基准） |
| 原生 `json_schema` | 400，DeepSeek 当前不支持 |
| 原生 `json_object` | 200，可用；不校验 schema |
