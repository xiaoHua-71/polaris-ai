## 已知风险

### 1. 版本很新，资料与示例可能滞后

Boot 4 + Spring AI 2.x 都属于较新的稳定线。网上大量示例基于 Boot 3 + Spring AI 1.x，直接照搬可能遇到：

- 模块 / starter 拆分变化
- 配置项改名
- 测试依赖变化
- 底层 HTTP 客户端从自研实现换成官方 SDK

**应对**：以当前版本的依赖 POM、源码和启动日志为准；文档里所有官方类名都标注版本前提。

### 2. 错误不可诊断

无 key、错 key、错 model、网络失败，目前对外都表现为 HTTP 500 或笼统的 400。调用方无法区分，排障只能看服务端日志。

**应对**：M8 统一错误映射；在此之前，验证记录里保留真实根因。

### 3. 启动成功 ≠ 配置正确

空 key 也能启动。这意味着部署时「进程起来了」不能作为健康判据。

**应对**：健康检查与配置校验纳入 M8；在文档和启动说明里明确这一点。

### 4. 同步调用与线程占用

`/chat` 的 `call()` 仍是阻塞的，会占用 Servlet 工作线程；`/chat/stream` 已改为 SSE + Reactor 订阅，请求线程在返回 emitter 后释放。两条路径都没有并发压测，**不能声称性能可接受**。

**应对**：M8 工程化时压测；需要时引入超时、隔离与限流。

### 5. 成本不可见

没有 token 统计和费用记录。对话越长、调用越多，成本只能靠账单反推。

**应对**：M8 记录输入/输出 token 与单价；在此之前不跑批量调用。

### 6. 密钥管理

key 只存在环境变量里，这是对的；但一旦有人把真实 key 写进 yml 或日志，就会进入 git 历史。

**应对**：提交前检查 diff；错误日志不要打印请求头。

### 7. Windows 环境差异

中文编码、路径、端口残留进程都踩过或已知。这些不是业务风险，但会浪费大量排障时间。

**应对**：中文请求体走 UTF-8 文件；停止服务后检查端口；构建前固定 JDK 21。

## 决策记录（简版）

| 决策 | 选择 | 理由 |
|---|---|---|
| 框架 | Spring AI 官方，不用 Spring AI Alibaba | 目标是理解官方抽象；DeepSeek 走 OpenAI 兼容协议已足够 |
| 版本 | Boot 4.1.2 + Spring AI 2.0.2 | 当前稳定线，且 starter 与 Boot 版本对齐 |
| 模型服务 | DeepSeek 官方 | 已有可用 key；OpenAI 兼容，迁移成本低 |
| 接口前缀 | `/api` | 与 star、salary-leap 习惯一致，端口隔离 |
| 统一响应信封 | 暂不引入 | 先保留原生 HTTP 语义；避免过早套壳，M8 再定 |
| 文档 | docs/ 编号 + 五段式 | 与 star 项目一致，方便对照 |
